# TomorrowTOU

Настольная университетская система: нативный JavaFX/FXML frontend и отдельный Spring Boot REST API на Java 21. Источник требований — [docs/TZ.md](docs/TZ.md); дополнительная роль `STAFF` реализована по уточнению заказчика. HTML в `prototype/` используется как визуальный и сценарный ориентир.

## Запуск

Нужны JDK 21, Python 3, curl, Docker с Compose, доступ к Maven Central при первой сборке. Maven устанавливать отдельно необязательно: `mvnw` использует установленный Maven или загружает версию 3.9.11. В этом рабочем окружении скрипт также обнаруживает ранее закэшированные JDK/Maven.

```sh
./scripts/docker-up.sh          # PostgreSQL + API backend + Adminer
./scripts/frontend.sh           # JavaFX на компьютере с графическим окружением
```

API: `http://localhost:18080/api`. Проверка готовности: `curl http://localhost:18080/api/health`. Adminer: `http://localhost:8081`, система PostgreSQL, сервер `postgres`, база и пользователь `tou`, пароль `tou-local`.

Порт API на компьютере теперь по умолчанию **18080**; внутри контейнера остаётся 8080. `docker-up.sh` ждёт готовности именно TomorrowTOU API после создания демонстрационного набора; `frontend.sh` проверяет сервер до запуска окна. Если порт занят, добавьте `API_PORT=18081` в `.env` и повторите обе команды. Скрипты читают один и тот же порт из `.env` (переменная окружения имеет приоритет). Другие сервисы на 8080 и данные PostgreSQL не удаляются.

Compose ждёт готовности PostgreSQL; первый запуск API применяет Flyway-миграцию и создаёт демонстрационные данные. Дождитесь `Started ApiApplication` в `docker compose logs backend` перед входом. Данные сохраняются в Docker volume `pgdata`; `docker compose down` сохраняет том. Конфигурацию Docker можно изменить через `.env` на основе `.env.example`.

|---|---|---|
| Администратор | `admin@tou.edu.kz` | `Tomorrow21!` |
| Преподаватель | `teacher@tou.edu.kz` | `Tomorrow21!` |
| Студент | `student@tou.edu.kz` | `Tomorrow21!` |
| Сотрудник | `staff@tou.edu.kz` | `Tomorrow21!` |

В панели входа выберите соответствующую роль. Демо-кнопка заполняет данные выбранного аккаунта и выполняет настоящую авторизацию. Если изменён `DEMO_PASSWORD`, задайте его и при запуске frontend или введите пароль вручную. Новое значение переменной не меняет уже созданные пароли: их меняет администратор в «Пользователях». «Запомнить меня» сохраняет только логин и роль; пароль и bearer token на диск не записываются.

Для запуска API локально, с PostgreSQL и Adminer в Docker:

```sh
docker compose up -d postgres adminer
./scripts/backend.sh            # ./mvnw -pl backend spring-boot:run
./scripts/frontend.sh           # отдельный терминал
```

`backend.sh` включает демо-наполнение для разработки, если переменные не заданы. Для другого подключения API используйте `TOU_API_URL` на стороне frontend и `DB_URL`, `DB_USER`, `DB_PASSWORD` на стороне backend. Например:

```sh
TOU_API_URL=http://localhost:18080 ./scripts/frontend.sh
DEMO_SEED=false DB_URL=jdbc:postgresql://localhost:5432/tou ./scripts/backend.sh
```

Образ сборки API — `maven:3.9.11-eclipse-temurin-21`, runtime — `eclipse-temurin:21-jre`; backend работает от непривилегированного пользователя. JavaFX запускается на хосте.

## Сборка и проверки

```sh
./scripts/compile-frontend.sh    # ./mvnw -pl frontend clean compile
./scripts/test.sh                # 10 launch tests + ./mvnw test: 126 unit/HTTP/contract tests
./scripts/build.sh               # ./mvnw clean verify
./scripts/integration-test.sh    # 20 дополнительных API/PG тестов; нужен Docker
./scripts/e2e-test.sh            # Compose + PostgreSQL IT + 4 native JavaFX E2E; DISPLAY/Xvfb
```

Для Windows предусмотрен `mvnw.cmd`; аналогичные команды: `mvnw.cmd -pl frontend javafx:run`, `mvnw.cmd -pl backend spring-boot:run`, `mvnw.cmd test`. Скрипты `.sh` предназначены для Linux/macOS. JavaFX 21 требует установленной графической системы; на Linux нужны GTK 3 и стандартные библиотеки X11. JVM и JavaFX должны соответствовать архитектуре компьютера.

Интеграционные тесты поднимают отдельный PostgreSQL 16 через Testcontainers, применяют настоящую миграцию, проверяют авторизацию, ограничения расписания, внешние ключи, доступ четырёх ролей и чтение документов Apache POI. Рабочую базу они не используют. Фактически выполненные проверки и ограничения окружения перечислены в [docs/AUDIT.md](docs/AUDIT.md).

## Структура

`frontend` и `backend` — независимые Maven-модули. Пакеты организованы по бизнес-фичам: `identity`, `students`, `teachers`, `groups`, `curriculum`, `schedule`, `attendance`, `grades`, `reports`, `profile` (frontend), `supervision`, `audit`, `dashboard`. В backend пакет `university` объединяет операции над связанными доменами и транзакции; `shared` содержит общую инфраструктуру. В frontend пакет `workspace` содержит навигацию и переиспользуемые таблицы/формы.

Модель включает `User`, `Student`, `Teacher`, `StudyGroup` (группа), `Subject`, `Lesson`, `Attendance`, `Grade`, `Semester`, `Room`, `LessonReview`, `AuditEvent`, `AccessSession`. Преподаватели и группы связаны с дисциплинами N:M. У студентов, занятий, оценок и посещаемости есть обязательные ссылки 1:N; внешние ключи защищают историю от удаления.

У всех изменяемых записей есть версия для защиты от потери одновременных изменений. PostgreSQL дополнительно запрещает пересекающиеся интервалы преподавателя, группы и аудитории через GiST exclusion constraints. Соседние интервалы разрешены; отменённые занятия не занимают ресурс.

## Права

| Действие | Администратор | Преподаватель | Студент | Сотрудник |
|---|---|---|---|---|
| Пользователи и справочники, CRUD | Да | Нет | Нет | Нет |
| Расписание | Всё, CRUD | Своё | Своей группы | Всё, просмотр |
| Дисциплины | Все | Только назначенные | Учебный план группы | Все, просмотр |
| Оценки и посещаемость | Всё, изменение | Свои занятия, изменение | Только свои, просмотр | Нет |
| Проверки преподавателей | Все, изменение | Свои, API просмотр | Нет | Все, изменение собственных проверок |
| Отчёты успеваемости | Все | Свои дисциплины | Свои | Нет |
| Аудит | Просмотр | Нет | Нет | Нет |
| Собственный профиль | Да | Да | Да | Да |

Сотрудник контролирует проведение занятий преподавателей, видит нагрузку и расписание, создаёт проверки с результатом и комментарием. Эта роль отдельна от администратора. Создание и изменение расписания остаются у администратора.

Пароли хранятся как BCrypt-хэши. В БД сохраняются SHA-256-хэши случайных токенов с временем жизни 8 часов. Выход отзывает текущий токен; смена пароля или изменение аккаунта администратором отзывает его сеансы. Права перепроверяются после изменения связей в запросе — смена `lessonId` не позволяет преподавателю изменить чужую оценку.

## Экраны и данные

Приветствие содержит три секции истории, регулируемый разделитель 45–70%, иллюстрацию процесса и правую панель входа. Кабинет содержит Dashboard, студентов, преподавателей, группы, расписание (неделя/таблица), посещаемость, оценки, отчёты, профиль, а также административные справочники, аудит и контроль преподавателей.

Таблицы поддерживают поиск, фильтры, сортировку всего загруженного набора, страницы по 10 записей и карточки с деталями. В карточке преподавателя есть расписание и нагрузка; в карточке группы — куратор, учебный план и доступный состав. API загружает доступные записи целиком; для больших университетских наборов потребуется серверная пагинация.

Dashboard рассчитывает показатели из доступных записей БД; при отсутствии оценок показывает «—». Среднее — арифметическое с округлением до десятой; оценки — целые 0–100. Аналитика содержит KPI, столбчатую диаграмму и круговую диаграмму. Сотрудник видит аналитику нагрузки и проведения занятий.

XLSX-ведомость фильтруется по группе/семестру, DOCX-справка — по студенту/семестру. Экспорт создаётся сервером с Apache POI. Все пользовательские действия выполняются через GUI; консоль служит для технических логов и запуска инструментов.

QR, лицо и Bluetooth в приветствии — иллюстрация из HTML-прототипа. ТЗ не содержит требований к реальному биометрическому или Bluetooth-пилоту; фактическая посещаемость вводится в журнале преподавателем/администратором.

## Логи и API

Log4j 2: `logs/app.log`, `logs/error.log`, `logs/audit.log`; в Docker — volume `apilogs`. Аудит также хранится в БД и доступен администратору. Пароли и токены не выводятся в логах.

Основные endpoints: `POST /api/auth/login`, `POST /api/auth/logout`, `GET/PUT /api/profile`, `GET /api/dashboard`, `GET/POST /api/records/{kind}`, `GET/PUT/DELETE /api/records/{kind}/{id}`, `POST /api/records/attendance/mark-all/{lessonId}`, `GET /api/reports/grades.xlsx`, `GET /api/reports/student.docx`. Для PUT обязательна `version`; для DELETE — параметр `version`. Авторизованные запросы используют `Authorization: Bearer <token>`.

Повторный аудит: [docs/AUDIT.md](docs/AUDIT.md). Проверено 120 Java-тестов и 10 тестов запуска в доступном окружении; полный PostgreSQL/JavaFX/POI прогон ещё не подтверждён.

Шрифты Manrope, Inter и IBM Plex Mono включены в ресурсы с лицензиями и загружаются перед FXML. Для отключения welcome-анимаций: `JAVA_TOOL_OPTIONS=-Dtou.reducedMotion=true ./scripts/frontend.sh`.

При ошибке входа: неверные учётные данные возвращают «Неверный логин или пароль», несовпадение роли при правильном пароле — отдельный ответ 403. `STUFF` в API принимается как `STAFF`. При существующей БД изменение TOU_DEMO_PASSWORD не меняет ранее сохранённые пароли: демонстрационный набор создаётся только на пустой таблице пользователей. Ошибки сервера больше не должны превращаться в 401 при ERROR-dispatch. Для диагностики серверных ошибок смотрите `docker compose logs backend` и `error.log`; пароли и токены в обращения не включайте.

Повторный вход после ошибки не требует ожидания: форма допускает один запрос одновременно и сохраняет введённый пароль для исправления. Демо-кнопка использует выбранную роль. При старте API до завершения инициализации возвращается 503 «API ещё запускается». В аудит пишется причина отказа (ACCOUNT_NOT_FOUND, ACCOUNT_DISABLED, PASSWORD_MISMATCH), без паролей и токенов.
