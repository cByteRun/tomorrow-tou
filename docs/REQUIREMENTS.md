# Требования: FR, NFR, UC

Источник истины — [TZ.md](TZ.md). Ни прототип, ни текущий код не добавляют требований в нормативные FR/NFR/UC. Разделы ТЗ указаны для каждого требования; технические решения и уточнения заказчика отделены ниже.

`[x]` означает наличие реализации в исходниках, **не успешную сквозную приёмку**. `[ ]` означает незакрытое требование. Выполненные проверки и ограничения находятся в [AUDIT.md](AUDIT.md), соответствие коду — в [ARCHITECTURE.md](ARCHITECTURE.md), план приёмки — в [ROADMAP.md](ROADMAP.md).

## FR — функциональные требования

- [x] **FR-01 — Авторизация.** Пользователь вводит логин и пароль и переходит в интерфейс своей роли: ADMIN, TEACHER, STUDENT, STUFF. Источник: ТЗ §1, §3.1. Приёмка: корректные данные открывают кабинет соответствующей роли; некорректные данные не дают доступ.
- [x] **FR-02 — Dashboard.** Статистика из БД, занятия сегодня, средний балл и диаграмма. Источник: §3.2, §5, §6. Приёмка: показатели соответствуют данным БД и изменяются после изменения исходных данных; заранее прописанных значений нет.
- [x] **FR-03 — Студенты.** Таблица, поиск, фильтры, карточка и CRUD студентов. Источник: §3.3. Приёмка: разрешённые операции создания, просмотра, изменения и удаления отражаются в таблице и карточке.
- [x] **FR-04 — Преподаватели.** Просмотр дисциплин, расписания и нагрузки преподавателя. Источник: §3.4. Приёмка: карточка отражает назначения и занятия выбранного преподавателя.
- [x] **FR-05 — Группы.** Просмотр состава группы, дисциплин и куратора. Источник: §3.5. Приёмка: данные связаны с выбранной группой и сохраняются в БД.
- [x] **FR-06 — Расписание.** Представление расписания таблицей и календарём. Источник: §3.6. Приёмка: один набор занятий отображается в обоих представлениях.
- [x] **FR-07 — Конфликты расписания.** Автоматически обнаруживать пересечения занятий преподавателя и аудитории. Источник: §3.6, §5. Приёмка: конфликтующее назначение отклоняется с понятной причиной; неконфликтующее сохраняется.
- [x] **FR-08 — Посещаемость.** Отметка присутствия студента по занятию. Источник: §3.7. Приёмка: сохранённая отметка принадлежит выбранным студенту и занятию и видна в журнале после обновления.
- [x] **FR-09 — Оценки и средние.** Выставление и редактирование оценок, расчёт среднего балла студента, группы и дисциплины. Источник: §3.8, §5. Приёмка: средние пересчитываются по доступным сохранённым оценкам, а не по заранее заданным числам.
- [x] **FR-10 — Отчёты.** Экспорт реальных данных в Excel-ведомость XLSX и Word-академическую справку DOCX. Источник: §3.9, §5. Приёмка: оба документа открываются и содержат данные выбранного доступного набора из БД.
- [x] **FR-11 — Профиль и выход.** Экран данных пользователя/настроек и выход из системы. Источник: §3.10. Приёмка: отображаются данные текущего пользователя; после выхода кабинет требует повторного входа.
- [x] **FR-12 — Работа со списками.** Поиск, фильтрация, сортировка и пагинация либо разумная загрузка данных. Источник: §1, §5. Приёмка: фильтры и сортировка применяются к доступному набору, результаты доступны через страницы или согласованную разумную загрузку.
- [x] **FR-13 — Валидация и ошибки.** Проверка обязательных полей и понятные сообщения через Alert/Dialog рядом с действием пользователя. Источник: §5, §6. Приёмка: некорректный ввод не сохраняется, сообщение объясняет, что исправить.
- [x] **FR-14 — Подтверждение опасных действий.** Подтверждать удаление, отмену и другие применимые опасные операции. Источник: §5. Приёмка: отказ в диалоге не изменяет данные. «Списание» не создаёт отдельный домен: в ТЗ оно приведено как пример применимой операции.
- [x] **FR-15 — Действия таблиц.** Доступные пользователю действия «Добавить», «Изменить», «Удалить/Отменить». Источник: §6. Приёмка: разрешённое действие открывает форму/подтверждение и изменяет данные; запрет проверяется также сервером.
- [x] **FR-16 — Собственные оценки студента.** Студент видит только собственные оценки. Источник: §5. Приёмка: чужие оценки недоступны через интерфейс, прямой запрос карточки и экспорт.
- [x] **FR-17 — Свои дисциплины преподавателя.** Преподаватель видит только свои дисциплины. Источник: §5. Приёмка: список дисциплин ограничен назначениями текущего преподавателя.
- [x] **FR-18 — Навигация.** Главное окно с боковым или верхним меню и понятными переходами между разделами. Источник: §1, §6. Приёмка: пользователь переходит между доступными экранами через GUI.

## NFR — нефункциональные требования

- [x] **NFR-01 — Настольный GUI.** Java и JavaFX, FXML / Scene Builder; полноценное настольное графическое приложение. Источник: §1, §2. Scene Builder — средство редактирования FXML, ТЗ не требует его присутствия в runtime.
- [x] **NFR-02 — Backend и ORM.** Spring Boot, Service Layer, Spring Data JPA / Hibernate. Источник: §1, §2. Приёмка: GUI обращается к сервисам, работа с БД выполняется через ORM, бизнес-правила находятся на сервисном уровне.
- [x] **NFR-03 — Хранилище.** PostgreSQL или MySQL в стеке; конкретизировано PostgreSQL в Docker в §4. Источник: §1, §2, §4. Выбран PostgreSQL; дополнительная реализация MySQL не требуется.
- [x] **NFR-04 — Модель данных.** Не менее 8 сущностей, все 10 перечисленных в ТЗ: User, Student, Teacher, Group, Subject, Lesson, Attendance, Grade, Semester, Room; связи 1:N и N:M, ограничения целостности. Источник: §2, §4. Приёмка: схема и ORM соответствуют друг другу, связанные данные не допускают нарушения ограничений.
- [x] **NFR-05 — Надёжность операций.** Валидация, обработка исключений, транзакции. Источник: §2. Приёмка: неуспешная бизнес-операция не оставляет частично сохранённые данные.
- [x] **NFR-06 — Журналирование.** Log4j 2, `app.log`, `error.log` и аудит. Источник: §2. Приёмка: технические события, ошибки и действия доступны в соответствующих журналах.
- [x] **NFR-07 — Технология экспорта.** XLSX и DOCX формируются Apache POI. Источник: §2. Приёмка: документы создаёт POI по реальным данным, см. FR-10.
- [x] **NFR-08 — Тестирование.** JUnit, минимум 25 содержательных тестов. Источник: §2. Приёмка: тесты проверяют бизнес-правила и дают воспроизводимые результаты; наличие исходника теста не считается успешным запуском.
- [ ] **NFR-09 — Git и README.** История разработки по этапам и README. Источник: §2. README и три реальных коммита есть; полнота истории всех этапов не подтверждена. Историю задним числом не выдумывать.
- [x] **NFR-10 — Интерфейс и аналитика.** Не менее 8 полноценных экранов, единый современный стиль, таблицы, формы, диалоги, минимум 2 визуальных элемента аналитики. Источник: §1, §3, §6. В ТЗ перечислены 10 экранов; реализованы все 10. Визуальная приёмка ещё не выполнена.
- [x] **NFR-11 — Пользовательские операции через GUI.** Консоль используется только для технических логов, без пользовательских операций. Источник: §1. Команды сборки/запуска — инструменты разработчика, не интерфейс бизнес-операций.

ТЗ не задаёт SLA, время ответа, объём нагрузки, числовую цель покрытия тестами или отдельный обязательный веб-интерфейс: такие требования здесь не добавлены.

## UC — пользовательские сценарии

Акторы — четыре роли FR-01. Для операций без точного распределения прав в ТЗ используется разрешённый ролью набор; конкретная текущая политика отмечена как решение реализации в [RBAC](RBAC.md). Предусловие UC-02–UC-10: пользователь вошёл, нужные исходные записи существуют.

- [x] **UC-01 — Вход в свой кабинет** → FR-01; NFR-01, NFR-02. Актор: любая роль. Поток: выбрать роль → ввести логин/пароль → войти → получить свой интерфейс. Альтернатива: ошибка данных/роли оставляет пользователя на форме с объяснением. Результат: авторизованный кабинет.
- [x] **UC-02 — Обзор учебных показателей** → FR-02, FR-18; NFR-10. Актор: любая роль. Поток: открыть Dashboard → просмотреть статистику, занятия сегодня, средний балл и диаграммы. Альтернатива: пустой набор не подменяется выдуманными числами. Результат: обзор текущих доступных данных БД.
- [x] **UC-03 — Работа со студентами** → FR-03, FR-12–FR-15; NFR-05. Актор: пользователь с доступом к студентам; CRUD — пользователь с правом изменения. Поток: найти/отфильтровать запись → открыть карточку → создать/изменить/подтвердить удаление → обновить список. Альтернативы: неверный ввод, отказ от удаления или отсутствие прав не изменяют запись. Результат: просмотр или сохранённое разрешённое изменение.
- [x] **UC-04 — Просмотр преподавателя** → FR-04, FR-17; NFR-04. Актор: пользователь с доступом к преподавателю. Поток: выбрать преподавателя → просмотреть дисциплины, расписание, нагрузку. Ограничение: преподавателю доступны только его дисциплины. Результат: связанные данные выбранного преподавателя.
- [x] **UC-05 — Просмотр группы** → FR-05; NFR-04. Актор: пользователь с доступом к группе. Поток: выбрать группу → открыть состав, дисциплины, куратора. Результат: сведения о выбранной группе в пределах прав доступа.
- [x] **UC-06 — Работа с расписанием** → FR-06, FR-07, FR-13–FR-15. Актор: пользователь с доступом к расписанию; изменения — пользователь с правом назначения. Поток: открыть таблицу/календарь → при изменении указать преподавателя, аудиторию и время → сохранить → обновить расписание. Альтернативы: конфликт преподавателя/аудитории отклоняется; отмена требует подтверждения. Результат: просмотр либо неконфликтующее сохранённое назначение.
- [x] **UC-07 — Отметка посещаемости** → FR-08, FR-13. Актор: пользователь с правом ведения журнала. Поток: выбрать занятие → студента → отметку присутствия → сохранить → проверить журнал. Альтернатива: неверные связи/отсутствие прав отклоняются. Результат: отметка для конкретного занятия и студента.
- [x] **UC-08 — Оценки и средние** → FR-09, FR-13, FR-16. Актор: преподаватель/администратор для изменения; студент для собственных оценок. Поток: открыть разрешённый журнал → выставить/изменить оценку либо просмотреть свои оценки → увидеть пересчитанные средние. Альтернатива: запрос чужих оценок студентом отклоняется. Результат: сохранённые оценки и рассчитанные показатели в рамках доступа.
- [x] **UC-09 — Получение отчёта** → FR-10, FR-16; NFR-07. Актор: пользователь с правом экспорта. Поток: выбрать доступный набор → Excel-ведомость или Word-справку → сохранить файл → открыть документ. Альтернатива: недоступный набор отклоняется, ошибка выгрузки показывается пользователю. Результат: XLSX/DOCX с реальными доступными данными.
- [x] **UC-10 — Профиль и выход** → FR-11; NFR-11. Актор: любая роль. Поток: открыть профиль/настройки → просмотреть свои данные → выйти. Результат: кабинет закрыт и следующий доступ требует входа.

## Уточнения заказчика вне нормативных FR/NFR/UC

Эти пункты имеют источник в сообщениях заказчика, а не в тексте ТЗ. Их нельзя выдавать за новые обязательные требования исходного ТЗ. Roadmap и архитектура ссылаются на них отдельно.

| ID | Уточнение | Статус исходников / приёмки |
|---|---|---|
| U-01 | Разделить frontend/backend и следовать package-by-feature | Реализовано; общий оркестратор UniversityService описан как ограничение структуры |
| U-02 | PostgreSQL и API в Docker, Adminer, Java 21/Maven, mvnw и скрипты запуска/тестов/сборки | Реализовано; реальный запуск Docker в среде агента не подтверждён |
| U-03 | Повторить финальный HTML welcome в JavaFX 1:1, включая шрифты и плавные анимации | Реализованы элементы и анимации; 1:1 не принято |
| U-04 | Сотрудник контролирует преподавателей; администратор — отдельная роль | Реализован домен supervision; STUFF из ТЗ — синоним STAFF в коде/API |
| U-05 | Добавить unit и сквозные E2E проверки, перепроверить вход | Unit/HTTP выполнены; полноценный PostgreSQL/JavaFX E2E не подтверждён; пользовательский непостоянный отказ не воспроизведён |

Реальная биометрия, камера, QR-сессии и Bluetooth не включены в FR: в welcome это иллюстрация прототипа. POSTMVP не превращает их в обязательную реализацию.
